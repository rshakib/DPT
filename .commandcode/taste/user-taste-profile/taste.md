# User Taste Profile
- Expects thorough, complete reading of all project files before making changes — "read carefully" means don't skip or sample, read everything. Confidence: 0.8
- Values keeping project documentation (`PROJECT_DOCUMENTATION.md`) accurate and fully in sync with the actual codebase; expects discrepancies to be corrected comprehensively across all relevant sections. Confidence: 0.75
- Communicates in short, informal English; expects the assistant to infer intent from terse, typo-laden instructions ("frather", "bacause") without asking for clarification. Confidence: 0.7
- Often writes in Bengali (Bangla romanized) mixed with English; expects the assistant to understand Bengali transliteration seamlessly without switching or asking for English. Confidence: 0.85
- Wants the assistant to respond in English even when they write in Bengali — explicitly said "ans in english". Accepts understanding Bengali input but prefers English-language responses from the assistant. Confidence: 0.9
- Strongly prefers non-breaking, incremental changes — repeatedly and explicitly asks to avoid harming running code or introducing errors ("without hamparing runnig code and without error"); asked this across three separate conversations. Expects new features to coexist safely with existing working flows and wants changes confined to error/failure paths only. Confidence: 0.9
- Works within free-tier infrastructure constraints (Render, Supabase) and prefers practical, cost-zero solutions to keep services alive; open to hybrid in-app + external-tool approaches. Confidence: 0.8
- Wants critical, gap-analysis style reviews of plans and code — prefers numbered lists comparing proposed design against actual implementation state, with specific actionable issues (not just praise). Confidence: 0.8
- Follows an audit-first workflow: wants a full audit + report covering ALL related flows (not just the reported issue), then explicitly waits for their approval ("ami bolle fix korbe") before any fixes are applied. Expects the assistant to NOT auto-fix during the audit phase — report first, fix on instruction. Confidence: 0.85
- When reporting a bug, expects the assistant to audit ALL similar patterns across the entire codebase (not just the reported instance) and present a comprehensive report — e.g., "fix fetch error in send-money" means grep and audit every transaction flow for the same pattern. Confidence: 0.8
- Prefers server-side self-sufficiency — instinctively asks whether backend can handle concerns independently without requiring the client app to be active; favors pushing responsibility to the server to reduce client dependency. Repeatedly asks "if I add this to backend, will it work without opening the app?" — wants backend to be the always-on layer. Confidence: 0.8
- Expects honest, upfront caveats about limitations of proposed solutions — wants to know what does NOT work or what edge cases remain, not just what works. Values direct "this does NOT solve X" explanations. Confidence: 0.75
- Wants all user-facing text — notifications, popups, alerts, button labels — in Bangla (Bengali), not English. Explicitly asked for Bangla popup notifications for offline transaction results. Confidence: 0.85
- Every UI component (including modals, popups, overlays) must respect the app's theme system (Classic + Sol themes, dark mode support) — no hardcoded colors or styles that clash with the active theme. Explicitly complained that "popup notification UI app er UI er sathe match kore na." Confidence: 0.9
- Expects transaction type labels to be specific and descriptive (e.g., "Send Money to @x", "Mobile Recharge (GP)", "Merchant Payment to @y") — rejects generic "Payment to @someone" for every transaction type. Wants distinct labeling per flow. Confidence: 0.85
- Values polished, visually cohesive UI — explicitly asks for "sundor koro app er sathe mile emn" (make it beautiful, match the app). Cares about animations, spacing, and overall aesthetic quality, not just functionality. Confidence: 0.8
- Sensitive UI elements (transaction popups, reconciliation alerts, financial info) must NOT be shown before the user has authenticated (PIN + biometric) — explicitly flagged the popup appearing on the lock screen as a bug. Expects gated rendering behind `isAuthenticated && !isLocked` checks. Confidence: 0.9
- Expects clean state transitions in transaction data — no duplicate or orphaned records when transactions change state (e.g., offline→success should update or delete the offline row, not create a second row alongside it). Reported duplicates for both online-success and offline-failed scenarios, expecting exactly 1 record per transaction regardless of outcome. Confidence: 0.85
- When requesting UI work, explicitly scopes it as "only ui" — expects purely visual/design changes with no logic, backend, or functional modifications. Treats UI polish as a separate task from feature/bug work. Confidence: 0.8
- Prefers minimal, clean result/status screen headers without branding — when they first asked to replace a small logo with styled text "DPT" and then immediately removed the text too, showing they want the status and amount to be the visual focus with no brand clutter. Values cleanliness over branding on confirmation screens. Confidence: 0.8
- Prefers white/light solid backgrounds over gradient backgrounds for full-page screens like the lock screen — explicitly said "background colour white e valo" after seeing a gradient version. Leans toward clean, light surfaces rather than heavy branded gradients. Confidence: 0.85
- Hates wasted whitespace on the sides of full-page form layouts — expects forms and content screens to fill the screen width with no empty margins. Complained "full page pacce na... pashe kahli kahli lage" (doesn't fill the page, looks empty on the sides). However, for numpad grids on dedicated screens (like lock screen), prefers comfortable side padding (bKash-style) rather than edge-to-edge — explicitly asked "side arektu gap daw." The context determines the whitespace preference: content forms = edge-to-edge; numpads/input grids = centered with breathing room. Confidence: 0.8
- Prefers minimal lock screens without showing the user's name or avatar — explicitly said "user name show korar dorkar nai" (no need to show username). Wants just a simple hint text and the PIN dots. Confidence: 0.85
- Prefers larger numpad key font sizes — finds very small keys too cramped, iteratively bumped from 22px → 28px → 32px until satisfied. Prefers digits to feel prominent and easy to tap. Confidence: 0.85
- When designing UI, sends real app screenshots (e.g., bKash) as design references and asks the assistant to replicate the layout/structure while applying their own app's colors and branding — "eta reference hisabe dhore degin koro... colour grading ei app moto hobe image ta only reference." Treats the reference image as a wireframe/layout guide, not a pixel-perfect copy target. Confidence: 0.85
- Prefers flat, borderless numpad layouts (bKash-style) — numbers displayed without circular keys, bordered boxes, or heavy visual containers. Wants the digits to feel integrated into the page rather than sitting in separate card-like elements. Confidence: 0.8
- Prefers underline-style PIN input fields over dot-circle indicators — likes a single underline with masked dots (••••) and a fingerprint icon on the right, rather than the traditional 8-circle dot pattern. Considers this cleaner and more modern. Confidence: 0.8
- Prefers a "Next" / explicit action button pattern over auto-submit on PIN entry screens — wants a visible "Next →" button that activates when PIN length is reached, rather than silently auto-submitting. Confidence: 0.75
- Expects visual consistency across screens — wants the lock screen (and other entry screens) to share the same large logo, slogan, and branding treatment as the login page. Explicitly said "login page er moto" to enforce this cross-screen consistency. Also requested the same custom numpad (1-9, 0, X) be reused on the login page that was built for quick-unlock, wanting identical input patterns across all PIN-entry screens. Confidence: 0.9
- Demands strict sequential authentication — when session is saved, PIN must always be entered first AND biometric scanned second, with no shortcuts or bypasses (no fingerprint icon shortcuts to skip PIN). Both factors are mandatory, never optional. Reiterated this requirement multiple times until all shortcut paths were removed. Confidence: 0.9
- Prefers authentication screens (login, quick-unlock) to have NO back buttons — explicitly requested removing back arrows from both the login page and quick-unlock page. Treats these as terminal entry points where back navigation is unwanted. Confidence: 0.85
- Prefers server-authoritative identity fields (e.g., full name from registration) to be read-only/non-editable in the app — explicitly said "eta editable hobe na" (should not be editable). Does not want users to set custom display names; the registered full_name from DB1 is the single source of truth shown on dashboard, profile, and settings. Confidence: 0.85
- Prefers a local-first-then-sync pattern for user personalization data (profile images, display name, settings) — SQLite for fast/offline access, DB1 (server) as the durable backup. Initially wanted SQLite-only ("eita only sql lite ei save thabe"), but later requested DB1 sync too ("eta save hobe db te. db 1 e"), settling on a hybrid: save to SQLite instantly for offline speed, then sync to DB1 in the background as the source of truth. Confidence: 0.85
- Prefers the "sol" (orange) theme as the app's default over "classic" — explicitly requested "theme sol ke defalut kore daw" (make sol theme default). Confidence: 0.85
- When planning large architectural changes, prefers pushing heavy work to the backend while minimizing mobile app changes — explicitly stated the mobile app stays untouched except for one feature (registration flow), and all major refactoring happens server-side. Wants to confirm feasibility and approach ("eta possible?? eta kivabe korbe bole vabcho") before any implementation starts. Confidence: 0.85
- Strongly dislikes long waits for plan generation or sub-agent tasks — gets frustrated when a response takes 20+ minutes; expects the assistant to deliver plans directly and quickly rather than spinning up slow sub-agents. If a tool call times out or stalls, prefers the assistant to abandon it and produce the output inline. Confidence: 0.9
- Prefers exact-length validation over minimum-length validation for PINs and codes — explicitly corrected "minimum 6" to "exactly 6". Wants precise, fixed-length constraints rather than flexible minimums. Confidence: 0.85
- When explicitly asking to "audit and fix" in one request (e.g., "audit koro dekho keno hocce and thik o kore felo"), expects root-cause analysis AND immediate fix in a single pass — no waiting for separate approval. This contrasts with their normal audit-first workflow where fixes await approval; the combined phrasing signals permission to act immediately. Confidence: 0.75
- Prefers auto-bootstrapping systems — wants the backend to detect missing database tables on first run and create them automatically via Python code, not print SQL for manual execution. Only the `.env` file should be configured manually; everything else should self-initialize. Reiterated by asking the agent to proactively run the backend and diagnose issues ("tmi backend run koro and dekho ki issu"), expecting fully automated resolution rather than manual SQL instructions. Confidence: 0.9
- Expects the assistant to execute commands directly ("you run") rather than providing step-by-step instructions for the user to copy-paste. When a restart, install, or other shell action is needed, prefers the assistant to just do it via tool calls — not list bash commands and say "run these yourself." Confidence: 0.85
- Before implementing a major new feature (e.g., NFC), explicitly requests a full backup copy of the project directory so the working code is preserved — "make one more backup and file so that now running code intact then implement". Treats backups as a prerequisite gate before risky feature work begins. Confidence: 0.85
- Prefers new features to be thin gateway layers that route into existing flows rather than building parallel standalone systems — when adding NFC, explicitly simplified it to just show send/receive options where "Send" navigates to the existing send-money screen and "Receive" waits for NFC tap, instead of having NFC manage its own amount entry and transfer logic. Confidence: 0.8
